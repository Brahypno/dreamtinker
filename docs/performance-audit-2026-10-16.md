# DreamTinker 性能排查记录（2026-10-16）

本轮重点是启动、内存及主要运行路径。依据为当前源码、本地 Forge/TConstruct 依赖源码，以及 2026-10-15 的 `run/logs/latest.log`、`run/gc.log`。日志早于本轮修改，不是修改前后对照实验。

## 10 月 16 日启动实测：JFR

本轮实际启动开发客户端，记录从 JVM 启动到主菜单的 180 秒，未进入存档。使用 JDK 的 `profile` 配置；记录约 8.7 MiB，未记录 DataLoss 事件。Java 执行采样和原生方法采样分开统计，避免将不同采样周期和原生等待混为 CPU 占比。

| 分配调用栈 | 主要分布在流读取、数组复制、字符串、HashMap，以及 Mantle `ConnectedModel.resolveParents` | 指向资源读取与模型解析管线，需要按调用栈看归属，不能直接将全部分配记到 DreamTinker |

`Stitcher.Region.add` 属于 Minecraft 原版客户端。本次采样没有证明该瓶颈由 DreamTinker 引起，因此这里只保留为整合环境背景数据，已从本项目优化计划移除，不添加针对它的全局 Mixin。

## 其余主要路径：开销来源和下一步优先级

以下优先级按触发范围、频率及工作量判断，不表示已经测出 CPU 排名。

后续已落实的三项优化：

1. `DaylostJudgmentEvents.processDelayedAttacks`：已按世界组织延迟攻击，避免各维度遍历其他世界的条目；保留 10 tick 延迟、世界内入队顺序及重放保护，清理空列表及卸载世界。减伤标记 `REDUCED_ATTACKS` 仍沿用原逻辑。实际收益取决于排队数量。
2. `DeathShredder.onUsingTick`：已将电力不足的退出条件前移到空间查询之前，将目标排序推迟到实际攻击分支；燃料预备仍使用原有目标数量，保留空转耗能、零电耗配置和按距离攻击顺序。
3. `as_one.onInventoryTick`：已在完成原有计时、耐久修复逻辑后，对空效果集合直接返回，跳过流和快照构造；有状态效果时仍使用原过滤快照。属于小幅分配优化，尚无实测耗时收益。

`ShortEvents` 的广域查询、透视网格上传、电锯实际攻击及粒子开销仍需对应游戏场景采样。现有主菜单记录未覆盖这些行为；它们目前不是已证实的卡顿原因。当前也没有新的、可归因于 DreamTinker 的重大启动瓶颈或长期内存泄漏证据。

| 路径 | 开销来源、触发条件 | 当前结论 |
| --- | --- | --- |
| `ShortEvents.onChangeTarget` | 怪物切换目标时，可能在整个跟随范围内查询 LivingEntity，再检查装备效果、可攻击性和视线。即使附近没有相关修饰符，也会先做查询 | 优先采样密集怪物场景。现有装备快照已做到同实体同 tick 复用，但空间查询本身仍重复。引入持有者索引前需要确认装备、饰品及非玩家实体变化的维护成本 |
| `WallVisionRenderer` | 半径上限 32，对应 65³ = 274625 个候选坐标；默认每 tick 处理 8192 个，未提前达到高亮上限时需约 34 tick 完成一轮。最多保存 16384 个高亮 | 已有球外排除、区段调色板过滤、形状缓存、VBO 缓存、视锥裁剪。扫描预算未限制某一帧的全部脏网格生成和上传，应分开采样扫描与 `uploadIfDirty`；34 tick 是分摊周期，不是 CPU 耗时 |
| `DeathShredder.onUsingTick` | 持续使用时查询候选目标、按距离攻击，每次目标粒子反馈调用两次 `sendParticles` | 已提前处理缺电退出、仅在攻击分支排序。其余开销仍需多目标持续攻击采样，区分实体查询、伤害事件链及粒子发送；没有实际包数或字节数记录，不能直接宣称网络拥塞 |
| `voidPearlConversion.onWorldTick` | 原来每个服务端维度的 tick 都遍历同一张全局跟踪表，再过滤所属维度；每 5 tick 的下落判断位于遍历内部 | 后续已按世界分组：D 个 tick 维度、N 个跟踪实体，从约 D×N 次条目访问变为各维度总计 N，另有 D 次地图查询。实体与返航原点合并为一条记录，空分组及卸载世界直接移除；保留转化概率、检查间隔和返航参数 |
| `DaylostJudgmentEvents.processDelayedAttacks` | 原来每个维度扫描全局延迟攻击列表，再检查所属维度和到期时间 | 已按世界分组，并在世界卸载时清理对应列表。保留世界内原有扫描和执行顺序；未测得实际队列长度，不宣称它是主要瓶颈 |
| `BurdenBearer.onLivingDeath` | 原来每次死亡都查询附近玩家，先检查装备再判断死者是否为守护对象 | 后续已复用守护对象类型判断，在空间查询前排除不支持类型，并先检查守护关系再检查装备；效果强度、范围、持续时间保留 |
| `as_one.onInventoryTick` | 持有该修饰符的工具在有状态效果时建立过滤快照 | 已跳过空效果集合；实际分配量由工具数和效果数决定。有状态效果时仍保留删除前快照 |
| `NarcissusFluidFeedbackCache.rebuild` | JEI 重建时扫描 ItemStack 配料变体并复制后查询流体能力 | 是启动/重载阶段的分配来源。不能仅按 Item ID 去重，因为 NBT 可能决定流体内容；日志中整个 DreamTinker 配方回调不足 100 ms，本轮不扩大改造 |
| 拖尾、SlashOrbit 渲染 | 工作量随可见实体、采样点及层数增加 | 拖尾已有环形缓冲、延迟分配、工作数组复用和距离采样；SlashOrbit 已有距离细节控制。未发现应当立即重写的证据；大量弹幕时再测帧 CPU/GPU 时间 |
| 投射物追踪 | 寻敌范围查询、碰撞候选处理 | 已缓存有效目标，失去目标时每 4 tick 才重新扫描；非穿透最近命中也已有避免全量排序的实现，不重复实施已有优化 |
| 网络同步与声音 | 状态同步、持续声音管理 | 已检查的 BlockViewer 状态同步有重复值抑制，借用武器同步按事件触发；电锯声音实例已有缓存。未发现这些路径无条件每 tick 重发全部状态的证据 |

对 DreamTinker 资源 PNG 的实际文件头统计：

| 资源目录 | PNG 数量 | PNG 文件合计 | 按宽×高×4 换算的源图片像素量 |
| --- | ---: | ---: | ---: |

10206 张小图片提示开发资源目录的文件打开/解析工作值得采样，但数量本身不能证明启动瓶颈。源图片中还包含生成器素材，并非每张都作为游戏纹理加载；上述约 40 MiB 不能当作运行时内存占用。

实际日志中整个环境的方块图集为 8192×4096。若按 RGBA8 计算，单个基础层约 128 MiB，未含 mip、驱动开销、其他图集或复制；这只是容量换算，不是实测显存，也不是 DreamTinker 独占。JFR 已提供分配采样和 GC 后堆数据，但当前没有 heap dump、对象直方图或 GPU 采样，不能给出本项目各类对象的真实驻留比例。

本轮已处理有明确持有链的守护目标缓存。`EquippedModifierSnapshot` 的快照值只保存修饰符等级，不持有实体；拖尾的大数组也不是构造实体时就全部分配。没有把这些已有设计当作新的内存泄漏。
